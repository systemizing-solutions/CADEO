3. Design the shared product

Add merchant and service sources. Publish three related canonical models. Canonical means one agreed model for consumers.

input_merchantstutorial_merchantOne merchant ID

The connection model reads the two canonical models through explicit model_ref dependencies. Use LEFT joins. Keep D3 visible when S9 has no service record.

In the project ERD, Connection links to Device in the starter product. This conceptual link does not create a join or build dependency.

The source owners are Operations, Merchant Operations, and Service Operations. Review their keys and columns before you build.

Each physical dataset selects connection: source and a qualified table such as source.input_devices. Publication independently selects delivery.execution.connection: destination. Model references use the canonical outputs in the destination.

Discovery can skip canonical inputs before the first build. Check source data again after the build. The 24-hour freshness promise needs separate operational evidence.

4. Check and publish

Build the full product. Expect three connection rows. Key checks prevent duplicates. Reconciliation prevents unapproved row loss. Owner examples check meaning, not only SQL syntax.

Open acceptance evidence

In the editor, select Acceptance evidence. Check the real run manifest. A green test does not replace owner approval.

The schedule is metadata. CADEO does not start a scheduler. This tutorial reads a separate local SQLite source database directly and publishes to the destination. Direct cross-database builds currently support local SQLite files only.

5. Use the support queue

Find active connections with no service record. Expect one item: D3 at City Pharmacy, with service S9. Send it to Service Operations. Do not mark it inactive.

Support can act without joining three source tables. The data engineer can reuse the canonical models, rerun the build, and keep evidence of each check.

This queue does not measure revenue or prove payment success.

The build stops at the first failed check. Later checks can remain not run. Accepted-value checks alone cannot detect a reversed status rule.

To repair a real error, agree the rule with the owner, fix the mapping, rerun the checks, and keep the new evidence.
